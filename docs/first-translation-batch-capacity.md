# SMaLL-100 INT8 첫 번역의 배치 용량과 메모리 재사용

2026-11-18 (한국시간). 기준 실행 파일은 `v0.3.7`의 소스
`f70a3a8dc060a5107cf7c84c5c52ff230ee7f699`에서 빌드했다.
AMD EPYC 9V45 클라우드의 CPU 할당량은 4개였다. 동일한 SMaLL-100 INT8
모델로 새 프로세스를 실행했고 교정 기억과 디스크 번역 결과 재사용을 껐다.
모델 검증·로드부터 회차 순서대로 TXT를 저장하는 시간까지 포함했다.
원문은 고정된 HTML 사본을 사용했으며, OS 파일 캐시는 비우지 않았다.
[`v0.3.7` 릴리즈](https://github.com/P-JSL/Syousetu_Translate/releases/tag/v0.3.7)

## 배치 용량 비교

기존 번역기는 문장이 끝난 자리에 다음 문장을 넣는 반복 단위 배치를 쓴다.
한 번에 더 많은 문장을 처리하면 각 투영에서 같은 가중치를 더 많은 행과
공유할 수 있다. 동시에 살아 있는 문장 수가 늘면 인코더 상태와 디코더
K/V 저장 공간도 커진다. CPU 예산을 4개로 고정하고 SMaLL-100의 35화와
24화 전체 첫 번역으로 이 비용을 비교했다.

| 전체 작품 | 논리 작업자 | 시간 | 32개 대비 단축 | 최대 RSS 표본 |
| --- | ---: | ---: | ---: | ---: |
| 35화 | 32 | 64.221189922초 | 기준 | 1,117,904 KiB |
| 35화 | 64 | 51.438906658초 | 19.90% | 1,217,848 KiB |
| 35화 | 128 | 49.248435443초 | 23.31% | 1,326,596 KiB |
| 24화 | 32 | 93.307593712초 | 기준 | 996,428 KiB |
| 24화 | 64 | 77.991641240초 | 16.41% | 1,158,296 KiB |

각 행을 한 번씩 같은 기준 바이너리로 실행했다. 64개에서 RSS가
35화 97.60 MiB, 24화 158.07 MiB 증가했다. 35화를 128개로 늘렸을 때는
64개 실행보다 4.26% 짧고 106.20 MiB 더 컸다. CPU 예산이 4개 이상인
내부 CPU 엔진의 자동 용량은 64개로 설정했다. 예산이 더 작거나 CUDA를
선택한 자동 설정은 32개다. 작업자 수를 지정하면 그 값을 사용한다.

Orca는 토큰 반복마다 활성 배치의 요청을 갱신하고 선형층처럼 공유할 수
있는 작업을 묶는다. 기존 배치 스케줄러가 이 방식의 문장별 격리를
구현한다. Sarathi-Serve는 크고 불균일한 요청 때문에 활성 배치가
대기하는 문제를 다루며, CTranslate2는 배치 크기와 토큰 예산을 조정해
효율을 높이는 방법을 설명한다. 여기서는 양방향 인코더가 문장 전체를
읽는 구조를 유지하면서 동시 문장 수만 비교했다.
[Orca 논문](https://www.usenix.org/conference/osdi22/presentation/yu) ·
[Sarathi-Serve 논문](https://www.usenix.org/conference/osdi24/presentation/agrawal) ·

## 투영 결과 재사용

CPU에서 선형 투영이 새로 만든 F32 버퍼에 편향과 ReLU를 적용하거나,
기존 덧셈 순서인 `residual + (projection + bias)`로 결과를 쓴다. 두
경로 모두 투영의 버퍼를 저장소로 사용한다. 출력 원소가 `m × n`이면
후처리 단계마다 `4 × m × n`바이트의 임시 F32 출력 할당을 피할 수 있다.
이 식은 할당할 배열의 크기를 나타낸다. 실제 RSS는 배치에 동시에
살아 있는 텐서와 할당기의 재사용에도 영향을 받는다.
[oneDNN post-op 설계](https://uxlfoundation.github.io/oneDNN/dev_guide_attributes_post_ops.html)

두 실행 모두 작업자 64개를 사용했다. 대조에는 64개를 직접 지정하고
후보에는 자동 설정을 적용한 뒤 실행 로그에서 같은 CPU와 작업자 수를
확인했다.

| 작품 | 기존 할당 | 투영 버퍼 재사용 | 시간 단축 | 최대 RSS 표본 변화 |
| --- | ---: | ---: | ---: | ---: |
| 35화 | 56.469873191초 | 50.888896555초 | 9.88% | 70.75 MiB 감소 |
| 24화 | 78.127300887초 | 78.080502877초 | 0.06% | 10.99 MiB 감소 |

각 작품에서 두 실행을 연이어 한 번씩 비교했다. 24화의 시간 차이는
0.05초 미만이었다. 35화의 배치 용량 비교에서 기록한 기준 64개 결과와
여기서 기록한 대조 결과가 약 5초 달라, 서로 다른 비교의 단축률을
곱해서 최종 단축률로 계산하지 않았다.

## 최종 버전의 기본 설정 비교

`--jobs`를 생략해 `v0.3.7`과 `v0.3.8`의 기본값을 실제로 적용하고,
35화 전체를 연이어 한 번씩 실행했다. 두 프로세스의 CPU 예산은 4개였고
`--parallel-mode parallel`로 실행했다.

| 35화 첫 번역 | v0.3.7 | v0.3.8 |
| --- | ---: | ---: |
| 실행 로그의 작업자 | 32 | 64 |
| 모델 로드부터 TXT 저장까지 | 67.504283116초 | 54.478651599초 |
| 최대 RSS 표본 | 1,140,052 KiB | 1,114,996 KiB |

**19.30% 단축**, 최대 RSS 표본 24.47 MiB 감소였다. `cmp`로 전체 TXT를
비교하고 독립 검증기로 35화, 원문 6,248줄과 회차 순서를 확인했다.
이 결과는 위 CPU와 병렬 실행 조건에서 관측한 값이다.

## v0.3.9 이후 자동 배치 비교

동일한 24화의 저장 HTML을 사용해 자동 CPU 모드로 처음부터 번역했다.
AMD EPYC 9V45 클라우드에서 CPU 4개, 같은 SMaLL-100 INT8 모델을 사용했다.
두 빌드 모두 추론 계측을 켜고 교정 기억과 저장 결과 재사용을 껐다. 시간은
새 프로세스의 모델 검증과 로드부터 TXT 저장까지이며, HTTP 다운로드는 제외했다.
버전별 1회 측정이다.

| 항목 | v0.3.9 | 수정 버전 |
| --- | ---: | ---: |
| 자동 논리 문맥 수 | 64 | 최대 128 |
| 번역 및 TXT 저장 | 76.691초 | 70.220초 |
| 디코더 호출 수 | 2,751 | 1,196 |
| 디코더 안의 전체 어휘 투영 및 선택 | 22.961초 | 19.205초 |
| 최대 RSS 표본 | 1,117,068 KiB | 1,357,700 KiB |

자동 설정은 시범 문장을 두 경로로 번역하는 대신 유효한 고유 행 수를 보고
배치 여부를 고른다. CPU 예산이 4개 이상이면 다음 원문을 최대 32행 미리
인코딩하고, 짧은 문장에 더 많은 문맥을 제공한다. 인코더 묶음은 최대 2,048
토큰이다. 원문 길이와 각 문장의 생성 한도를 합친 예산은 45,184토큰으로
제한한다. 이 예산은 모델 가중치, 임시 텐서와 할당기 비용을 제외한 문맥별
예약량이다.

전체 시간은 8.44% 줄었고, 최고 메모리 표본은 235.0 MiB 늘었다. 두 TXT는
바이트 단위로 같았다. 독립 검사에서 24화와 원문 17,041줄, 내용이 있는
8,533줄의 번역 출력 및 순서를 확인했다. ezTrans XP 또는 GPU 실행은
이 비교에 포함되지 않는다. [24화 원문](https://kakuyomu.jp/works/16818622176193367283)
