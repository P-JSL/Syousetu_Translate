# 클라우드에서 측정한 SMaLL-100 INT8 첫 번역 시간

2026-11-18 (한국시간). 기존 실행 파일로 Kakuyomu 작품 35화 전체를
처음부터 번역하고 TXT에 저장하는 데 **45.975~46.477초**가 걸렸다.
기존 실행 파일 두 번의 중앙값은 **46.226초**다. 두 CPU 가속 후보는
각각 대조 실행보다 1.28%, 4.15% 오래 걸려 제거했다.
[측정 작품](https://kakuyomu.jp/works/11054822663814504924)

| 비교 | 기존 시간 | 후보 시간 | 시간 증가 | 기존 peak RSS | 후보 peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 어휘 투영에서 12행이 가중치를 공유 | 46.476602020초 | 47.072534070초 | 1.28% | 1,315,036 KiB | 1,256,100 KiB |
| AVX-512로 Q8 입력을 한 번에 준비 | 45.975167284초 | 47.882417840초 | 4.15% | 1,220,460 KiB | 1,260,252 KiB |

첫 후보는 넓은 어휘 투영에서 한 가중치 블록을 최대 12개 입력 행에
사용한다. 모든 어휘를 평가하며 각 점수의 정수 내적과 FMA 누적 순서를
유지한다. 두 번째 후보는 같은 블록 스케일과 반올림 규칙으로 오프셋
부호화를 패킹에 합친다. Q8 내적이 사용하지 않는 부분합 계산과 부호를
변환하는 추가 순회를 줄인다. 두 후보 모두 행렬 점수 회귀 시험을 통과했다.

## 측정 조건과 결과 검증

- AMD EPYC 9V45, CPU 할당량 4개, 기본 AVX-512 VNNI. 병렬 번역의 논리
  문맥은 128개이며 `CANDLE_NUM_THREADS=1`이다. 이 클라우드에 NVIDIA
  장치가 없어 RTX 4070 이상의 가속률은 실측하지 못했다.
- 최신 대조 소스는 `9e9a877be37e17b227769d0f4a8171d1570b77cd`다.
  후보별로 대조와 후보를 한 번씩 새 프로세스에서 실행했다. 교정 기억과
  디스크 번역 결과 재사용을 끄고, 같은 HTML 사본과 모델을 사용했다.
  모델 무결성 검증·로드와 순서대로 저장하는 TXT 쓰기는 시간에 포함했다.
  HTML 네트워크 다운로드는 제외했고 OS 파일 캐시는 비우지 않았다.
  실행 중 빌드나 다른 번역 작업을 병행하지 않았다.
  [측정 코드](../examples/benchmark_first_translation.rs)
- 네 TXT가 모두 607,026바이트로 같았다. 파일을 직접 비교했고, 별도
  검증기로 35화와 원문 6,248줄, 번역의 저장 순서를 확인했다. SHA-256은
  `a01ef9cac141faa625e740b353a6c2ed8800c9cec58f68e8fa5599fe879007bb`이다.
  [TXT 검증 코드](../examples/verify_saved_novel.rs)
- 10ms 간격으로 표본을 얻은 peak RSS는 첫 후보가 57.55 MiB 감소하고
  두 번째 후보가 38.86 MiB 증가했다. 각 후보는 검토 기준인 최대
  +512 MiB와 +25% 이내였다.

이전 v0.3.2의 35화 기록 163.1107초에 비해 현재 중앙값은 **71.66% 짧다**.
이는 서로 다른 시점의 버전 기록을 비교한 값이다. 최신 실행 파일을 기준으로
한 이번 두 후보에서는 추가 단축을 확인하지 못했다. 85~95% 추가 단축의
목표 시간은 약 6.93~2.31초다.
[v0.3.2 기준 기록](cpu-batching.md#v035-full-work-measurements)

## SMaLL-100 인코더 내부 실행 코드 검토

CPU 배치 인코더는 한 번에 얻은 Q·K·V 투영을 각각 연속 텐서로 복사하고
문장별 attention 결과를 다시 이어 붙인다. 후보는 K·V를 원래 투영의 열에서
읽고, 스케일을 적용한 Q에만 스레드별 작업 버퍼를 쓴다. 각 문장의 결과는
서로 겹치지 않는 출력 구간으로 바로 기록한다. 두 경로는 같은 행렬곱과
F32 softmax 함수를 사용한다. 실제 모델의 헤드 폭 64와 길이 1~192의
회귀 시험에서 attention 값이 비트 단위로 일치했다.

두 번째 후보는 문장마다 대략 길이의 제곱에 비례하는 attention 작업량을
계산한다. 개별 문장이 스레드 하나의 평균 작업량을 넘고 기존의 헤드
병렬화 기준도 충족하면, 헤드를 여러 스레드에 나눌 수 있는 기존 경로를
사용한다. 합성 입력으로는 길이 8~192의 128문장 배치 아홉 가지에서
복사를 줄인 경로의 attention 시간이 모두 짧았다. 이 진단은 행렬곱,
디코딩, 저장까지 포함하는 전체 번역의 가속률과 구분한다.

| 작업자 수 / 작품 | 후보 | 기존 | 후보 시간 | 관측 변화 |
| --- | --- | ---: | ---: | ---: |
| 128 / 24화 | 투영 직접 읽기 | 80.185799406초 | 71.985244520초 | 10.23% 단축 |
| 128 / 24화 | 긴 문장의 헤드 병렬 유지 | 76.012722117초 | 69.322018282초 | 8.80% 단축 |
| 128 / 35화 | 투영 직접 읽기 | 46.225884652초 | 49.977697496초 | 8.12% 증가 |
| 128 / 35화 | 긴 문장의 헤드 병렬 유지 | 46.225884652초 | 48.114418857초 | 4.09% 증가 |
| 32 / 35화 | 긴 문장의 헤드 병렬 유지 | 64.059857281초 | 58.155741045초 | 9.22% 단축 |

24화는 각 행에서 대조와 후보의 전체 실행을 한 쌍씩 측정했다. 128개
작업자의 35화 비교는 위에서 보관한 대조 두 번의 중앙값을 재사용했다.
따라서 이 두 행에는 시점이 다른 실행의 변동이 포함된다. 같은 24화의
대조 실행도 두 시점에서 4.17초 차이가 났다. 두 후보 모두 앞과 같은
고정 모델과 결과 재사용을 끈 상태로 전체 번역을 실행했다.
[24화 측정 작품](https://kakuyomu.jp/works/16818622176193367283)

24화에서는 독립 검증으로 17,041줄과 회차 순서를 확인했고 네 TXT가 모두
937,029바이트로 일치했다. SHA-256은
`095a4045e8430fcd844656235002212550582173cd753bec7779a5a8579c1992`이다.
두 후보의 35화 TXT 역시 위에 기록된 파일과 바이트 단위로 같았다.
24화 후보의 표본 peak RSS는 각각 40.91 MiB와 18.70 MiB 줄었다.

35화는 배포 기본값인 작업자 32개와 병렬 모드로 대조와 두 번째 후보를
연이어 한 번씩 실행했다. 두 TXT는 607,026바이트로 동일했고, 원문
6,248줄과 회차 순서를 검증했다. 표본 peak RSS는 1,028,652 KiB에서
1,074,900 KiB로 **45.16 MiB / 4.50%** 증가해 검토 범위 이내였다.

긴 문장의 헤드 병렬 처리를 보존하는 후보를 CPU 배치 인코더에 적용했다.
같은 조건을 연이어 비교한 작업자 32개의 35화에서 **9.22%**, 작업자
128개의 24화에서 **8.80%** 단축을 관측했다. 작업자 128개의 35화에서는
별도 시점 비교에서 단축을 확인하지 못했다. 85~95% 추가 단축과 RTX
4070 이상의 수치는 이 실측으로 확인되지 않았다.
