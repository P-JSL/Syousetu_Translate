# SMaLL-100 INT8 첫 번역의 60% 단축 조건

## 실측 시간에서 도출한 조건

기준은 `918f11f`의 클라우드 CPU 24화 첫 번역 67.810056992초다. 저장한
원문 HTML로 새 프로세스를 실행해 모델 검증·로드부터 TXT 저장까지 측정했다.
교정 기억과 디스크 번역 결과 재사용을 끄고, CPU 할당량은 네 개였다.
60% 단축에는 **27.124022797초 이하**가 필요하다.
[24화 원문](https://kakuyomu.jp/works/16818622176193367283)

서로 겹치지 않는 인코더 `E = 29.059818300초`, 디코더 `D = 35.629064685초`,
나머지 `R = 3.121174007초`의 합이 전체 시간이다. 어느 한쪽을 유지하면
그 단계만으로 목표 시간을 넘긴다. 나머지 시간을 고정하면 두 단계가 함께
충족해야 할 조건은 다음과 같다.

```text
E / encoder_speedup + D / decoder_speedup <= 0.4 * (E + D + R) - R
                                          = 24.0028487898 s
```

두 단계가 동일한 만큼 빨라지는 경우 최소 **2.695배**가 필요하다. 디코더
안의 어휘 투영·선택 18.443초를 완전히 없애도 49.367초가 남는다. 이런
범위는 한 단계나 한 커널 개선을 전체 단축률로 해석하는 오류를 피하게 해준다.
[Amdahl의 논문](https://doi.org/10.1145/1465482.1465560)

### 현재 CPU 연산에 대한 조건부 하한

같은 원문의 이전 계측에서 얻은 원문 약 129,800토큰과 디코더 약 127,437토큰을
사용한다. 모델 폭 `h=1024`, FFN 폭 `f=4096`, 투영 폭 `V=128112`에서
인코더 12층과 디코더 3층의 선형층 연산량을 추산한다. `x`는 원문 토큰 수,
`y`는 디코더 토큰 수다.

```text
M = 12*x*(4*h² + 2*h*f) + 3*(2*x*h² + y*(6*h² + 2*h*f)) + y*h*V
  ≈ 42.75 * 10^12 MAC
```

Zen 5 독립 명령 측정에서 512비트 `VPDPBUSD`, `VMULPS`, `VFMADD231PS`는
같은 FP01 실행 자원을 사용하며, 각각의 역처리량은 0.5사이클이다. 현재의
밀집 Q8 연산에서 16개 출력의 32개 곱을 처리하려면 `VPDPBUSD` 8개와
스케일 곱·누적 명령 2개가 필요하다. 이를 전체 밀집 선형 계산에 적용하면
64 MAC당 평균 1.25개 명령을 해당 자원에 예약하게 된다.

4개 코어를 각 3.5 GHz로 지속 사용한다고 가정해도 해당 명령의 실행만
약 **29.82초**다. 같은 구조로 24.003초 안에 들려면 이 이상적인 계산에서조차
약 4.35 GHz가 필요하다. 메모리 접근, 데이터 준비와 attention 비용은 계산에서
제외했다. 클라우드 코어의 실제 지속 주파수나 다른 하드웨어의 하한으로
해석할 수 없다. 같은 밀집 계산을 작은 캐시 최적화만으로 60% 가속하기
어려운 이유를 수치로 설명한다.
[Zen 5 정수 내적](https://www.uops.info/html-instr/VPDPBUSD_ZMM_ZMM_ZMM.html#ZEN5) ·
[스케일 곱](https://www.uops.info/html-instr/VMULPS_ZMM_K_ZMM_ZMM.html#ZEN5) ·
[부동소수점 누적](https://www.uops.info/html-instr/VFMADD231PS_ZMM_K_ZMM_ZMM.html#ZEN5)

## 위 조건을 사용한 구현

### CPU의 가중치 재사용

AVX-512 VNNI 후보는 출력 32열과 최대 24문맥을 묶고, 입력 성분 512개에
해당하는 가중치 구간을 각 문맥에서 재사용한다. 가중치 20,480바이트, 활성값
14,016바이트, 누적값 3,072바이트를 합친 데이터 크기는 **37,568바이트**로
측정 호스트의 48 KiB L1 데이터 캐시보다 작다. 실제 캐시 적중률은 주소 배치와
동시에 접근하는 다른 데이터에도 좌우된다. 행렬 크기와 마이크로커널에 맞춰
캐시 블록을 고르는 최근 연구를 참고했다.
[Cache-aware optimization, Cluster Computing 2025](https://doi.org/10.1007/s10586-025-05426-6)

출력 하나의 계산은 기존과 동일한 순서로 32개 원소의 정수 내적을 스케일링해 F32
FMA로 누적한다. 각 구간 사이에 저장하고 읽는 누적값은 이미 F32이므로
반올림 단계가 추가되지 않는다. 처음 누적값은 0이고, 같은 값으로 시작한
구간의 내적, 스케일, 누적 순서가 같으므로 다음 구간도 같은 값으로 시작한다.
이 귀납 관계가 끝까지 유지되어 타일로 묶어도 같은 결과를 얻는다. 2026년
프리프린트의 명제 1도 정수 범위와 스케일 구간, 누적 순서의 보존을 비트 일치의
충분조건으로 제시한다. 여기서는 기존 정수 내적의 실행 순서만 바꾼다.
[Beyond Accuracy, 명제 1](https://arxiv.org/abs/2609.39816)

네 작업자를 사용한 합성 행렬은 조건마다 기준·후보를 두 번씩 교대로 실행했다.
모든 출력 비트가 일치했다. 기준 평균과 후보 평균을 비교하면 어휘 투영
64문맥은 29.7%, 128문맥은 32.3%, 65문맥의 작은 FFN 하향 투영은 23.0%
짧았다. 512문맥에서 이득이 작거나 역효과가 난 FFN 행렬은 후보의 적용 범위에서
제외했다. 이 수치는 해당 행렬 연산의 소요 시간이다.

### GPU의 원문 K/V 저장 방식과 배치

CUDA는 인코더와 디코더의 행렬을 모두 같은 장치에서 처리한다. 입력 원문의
cross-attention K/V를 `[종류, 문맥*헤드, 원문 위치, 헤드 성분]` 순서로
보존한다. 순서를 바꾸어도 각 문맥·헤드의 원문 위치와 값, 패딩, 마스크는
같다. 따라서 실수 연산으로 정의한 attention은 이 레이아웃 변경에 대해
불변이다. 연속 문맥은 이미 보존한 K/V의 뷰를 직접 사용한다. 문장을 새로
입력할 때만 헤드 순서로 변환한다. FlashInfer의 KV 레이아웃과 위치 대응을
분리하는 설계를 참고했다. 실제 cuBLAS 계산은 스트라이드에 따라 F32 반올림이
달라질 수 있으므로 이전 CUDA 번역과의 비트 일치는 별도 실장비 검증 항목이다.
[FlashInfer, MLSys 2025 §3.1](https://proceedings.mlsys.org/paper_files/paper/2025/hash/dbf02b21d77409a2db30e56866a8ab3a-Abstract-Conference.html)

GPU의 자동 배치 크기는 KV 용량 계산에 따라 조절한다. 고정 모델의 문맥 하나에
필요한 F32 키·값의 상한은 `2 × 3 × 1024 × 4 × (194 + 512)`바이트다.
성장 중 이전·새 버퍼를 고려해 그 두 배를 문맥마다 계산하고, 나머지 작업
공간 4 GiB를 별도로 둔다. 실제 장치 측정 조건은
[CUDA 안내](gpu-rtx40.md)에 있다.

## 전체 24화 비교

기준 실행 파일과 후보 실행 파일을 각각 두 번 실행했다. 두 번째 비교는 후보를
먼저 실행했다. 두 빌드 모두 추론 계측을 켰으며 모델, 저장 원문, CPU 할당량,
자동 문맥 수 128과 명령 옵션을 맞췄다. 측정 중에는 같은 호스트에서 소스를
컴파일하거나 다른 추론을 실행하지 않았다. 메모리는 두 번의 최대 RSS 표본이다.

| 항목 | 기준 CPU | 후보 CPU |

| 첫 번역과 TXT 저장 1회차 | 67.810056992초 | 63.585284791초 |
| 첫 번역과 TXT 저장 2회차 | 62.339644087초 | 56.477641567초 |

중앙값은 **7.75% 단축**됐고, 회차별 비교에서는 각각 6.23%, 9.40% 단축됐다.
최대 RSS 표본은 약 36.24 MiB(2.94%) 증가했다. 첫 후보 실행의 인코더는
27.084초, 디코더는 32.809초였고, 디코더 안의 어휘 투영·선택은 16.971초였다.

확인했다. 목표 27.124초까지는 후보 중앙값에서 다시 약 2.21배 빨라져야 한다.
